# ADR 0010 — Worker و صف کارها (Redis + BullMQ)

وضعیت: پذیرفته‌شده

## زمینه

نقشه راه (بخش ۳) کارهای سنگین و زمان‌بر را به یک Worker جدا می‌سپارد: Workflow، Webhook، Import و ارسال انبوه
کمپین در فاز ۷. تا امروز Redis در compose بالا می‌آمد ولی هیچ‌چیز از آن استفاده نمی‌کرد، و هیچ کار زمان‌بندی‌شده‌ای
وجود نداشت (برای نمونه نشست‌های منقضی هرگز پاک نمی‌شدند).

## تصمیم

- **یک ورودی دوم در همان بسته:** `apps/api/src/worker.ts` یک NestJS application context (بدون HTTP) بالا می‌آورد و از
  همان `PrismaService`، پیکربندی و لاگر API استفاده می‌کند. Image همان است؛ فقط `command` فرق دارد
  (`node dist/worker.js`). بسته‌ی جدا برای فعلاً فقط دو بار Prisma generate و دو نسخه پیکربندی می‌شد.
- **BullMQ ۶ + ioredis**، نسخه‌ها دقیق قفل شده‌اند. نام صف‌ها و کارها در `infra/queue/queues.ts` است و قرارداد
  بین تولیدکننده (API) و مصرف‌کننده (Worker) را می‌سازد.
- **Redis برای API اختیاری است** (`REDIS_URL`). بدون آن API سرویس می‌دهد و کاری زمان‌بندی نمی‌شود. وقتی تنظیم
  شده باشد، `/health/ready` وضعیت Redis را هم می‌سنجد و با قطع بودن آن 503 می‌دهد. Worker بدون Redis بالا نمی‌آید.
- **زمان‌بندی با Job Scheduler:** `upsertJobScheduler` با شناسه ثابت، پس هر بار بالا آمدن Worker فقط همان یک
  زمان‌بند را به‌روز می‌کند و کار تکراری نمی‌سازد. کران cron به UTC است (ADR 0003): `۰۰:۰۰ UTC` یعنی ۰۳:۳۰ تهران.
- **اولین کار واقعی:** `purge-expired-sessions` روزانه؛ نشست‌هایی که منقضی (بیکاری یا مطلق) یا باطل شده‌اند و
  حداقل `SESSION_RETENTION_DAYS` (پیش‌فرض ۳۰) از مرگشان گذشته پاک می‌شوند. نشست زنده و تازه‌منقضی‌شده دست نمی‌خورد.
  منطق کار تابعی ساده روی Prisma است و بدون Redis هم قابل تست است.
- **تلاش مجدد:** هر کار تا ۳ بار با Backoff نمایی تکرار می‌شود؛ نتیجه‌ها محدود نگه داشته می‌شوند
  (`removeOnComplete: 50`، `removeOnFail: 200`).
- **سلامت Worker:** یک سرور HTTP کوچک روی `WORKER_PORT` فقط برای healthcheck کانتینر (`200` وقتی Worker در حال
  اجرا و Redis پاسخگوست). بیرون منتشر نمی‌شود.

## پیامدها

- فاز ۷ (Workflow، Webhook، `campaign_members`) با افزودن صف و پردازنده‌ی تازه به همین زیرساخت ادامه می‌دهد؛
  هر کار باید idempotent باشد، چون تلاش مجدد و اجرای هم‌زمان دو Worker ممکن است.
- Rate limit ورود هنوز در حافظه‌ی فرایند است (`common/rate-limiter.ts`). انتقالش به Redis مستقل از این ADR است
  و پیش از اجرای چند نمونه‌ی API لازم می‌شود.
- متریک طول صف در ADR 0019 اضافه شد؛ Tracing به بخش مشاهده‌پذیری (OpenTelemetry) موکول است.
- اگر Worker از کار بیفتد، کارها در Redis می‌مانند و پس از بازگشت اجرا می‌شوند؛ هشدار روی صف‌های عقب‌مانده
  بعداً با متریک‌ها اضافه می‌شود.
