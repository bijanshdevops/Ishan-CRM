# ADR 0006 — پیشنهاد، پیش‌فاکتور و قرارداد

- وضعیت: پذیرفته‌شده (فاز ۵ سند معماری)

## زمینه

فروش پس از فرصت به پیش‌فاکتور، پذیرش مشتری و قرارداد می‌رسد. باید مبالغ دقیق، شماره‌گذاری قابل‌اتکا، تاریخچه نسخه‌ها و خروجی قابل چاپ داشته باشیم.

## تصمیم‌ها

1. **مبلغ:** همه مبالغ عدد صحیح ریال (`BIGINT`)، در API رشته. نرخ مالیات به‌صورت basis point (۱۰۰۰ = ۱۰٪). محاسبه فقط در یک تابع خالص (`calculateQuoteTotals` در `@ishan/contracts`) که هم API و هم پیش‌نمایش UI از آن استفاده می‌کنند. ترتیب: جمع اقلام ← تخفیف ← مالیات (گرد کردن نیم‌به‌بالا به ریال) ← مبلغ نهایی. UI به تومان نشان می‌دهد و ورودی می‌گیرد؛ تبدیل ×۱۰ فقط در لایه UI.
2. **تمامیت در دیتابیس:** CHECK برای `total = subtotal - discount + tax`، `discount ≤ subtotal`، `line_total = quantity × unit_price`، بازه نرخ مالیات و ترتیب تاریخ‌ها. حتی اگر کد اشتباه کند، دیتابیس ردّ می‌کند.
3. **شماره‌گذاری:** جدول `document_counters` با `INSERT … ON CONFLICT DO UPDATE … RETURNING` در همان تراکنش ایجاد سند؛ قفل ردیف، شماره‌های یکتا و پیوسته را در هم‌زمانی تضمین می‌کند (تست هم‌زمانی ۶ درخواست). قالب نمایشی `QT-000012` و `CT-000003`.
4. **نسخه‌بندی:** هر نسخه یک ردیف است (`seq` مشترک، `version` افزایشی). فقط `DRAFT` ویرایش‌پذیر است. «نسخه جدید» فقط از `SENT`/`REJECTED` ممکن است؛ نسخه قبلی `SUPERSEDED` می‌شود. ایجاد نسخه با `SELECT … FOR UPDATE` قفل می‌شود تا دو نسخه هم‌زمان ساخته نشود. `ACCEPTED` نهایی است.
5. **انقضا:** وضعیت ذخیره نمی‌شود؛ `expired` در زمان خواندن از `valid_until` (تقویم تهران) محاسبه می‌شود و پذیرش پیش‌فاکتور منقضی ممنوع است.
6. **قرارداد:** فقط از پیش‌فاکتور `ACCEPTED`، یکی برای هر پیش‌فاکتور (یکتایی در دیتابیس)، مبلغ در لحظه ایجاد کپی می‌شود. انتقال وضعیت‌ها با compare-and-set.
7. **محصولات:** حذف نمی‌شوند، بایگانی می‌شوند تا پیش‌فاکتورهای قدیمی قابل توضیح بمانند. اقلام پیش‌فاکتور یک snapshot از شرح و قیمت‌اند و با تغییر محصول عوض نمی‌شوند.
8. **PDF:** از چاپ مرورگر (با استایل `@media print`) استفاده می‌شود، چون shaping و RTL فارسی در مرورگر درست است. تولید PDF سمت سرور نیازمند موتور رندر فارسی است و در این فاز عمداً انجام نشد.
9. **ورودی‌ها:** schemaهای درخواست `strict` هستند و فیلد ناشناخته رد می‌شود. schema ویرایش پیش‌فاکتور عمداً بدون مقدار پیش‌فرض است تا ویرایش جزئی تخفیف/مالیات را بی‌صدا ریست نکند (تست رگرسیون دارد).

## پیامدها

- ویرایش پیش‌فاکتور ارسال‌شده فقط با نسخه جدید ممکن است؛ این رفتار عمدی است.
- خروجی PDF فایلی روی سرور ذخیره نمی‌شود.
