# ADR 0024 — آدرس IP کلاینت پشت پراکسی Next

وضعیت: پذیرفته‌شده

## زمینه

اجرای محلی (Docker Desktop) نشان داد IP در گزارش ممیزی و نشست‌های فعال همیشه آدرس کانتینر `web` است. آزمایش روی
Next 16.4.2 با یک سرور echo پشت `rewrites()`:

- اگر درخواست ورودی `X-Forwarded-For` داشته باشد، Next آن را بدون تغییر به API می‌رساند.
- اگر نداشته باشد، Next آدرس socket کلاینت را اضافه نمی‌کند (فقط `x-forwarded-host` را می‌گذارد).

rewrite و `proxy.ts` و route handler در Next به آدرس socket دسترسی ندارند، پس اصلاح در کد وب ممکن نیست.

## تصمیم

- IP کلاینت وظیفه‌ی reverse proxy جلوی وب است. باید `X-Forwarded-For` را **بازنویسی** کند (مقدار `$remote_addr`)، نه
  اینکه به هدر ارسالی کلاینت اضافه کند، وگرنه کلاینت می‌تواند IP را جعل کند.
- زنجیره `reverse proxy → web (Next) → api` است، پس `TRUST_PROXY=1` (فقط یک hop معتبر: وب) درست است.
- در اجرای محلی بدون reverse proxy، API آدرس کانتینر وب (یا gateway داکر) را می‌بیند. این رفتار شناخته‌شده و فقط برای dev است.

## پیامدها

- بدون reverse proxy درست، محدودکننده‌های نرخ مبتنی بر IP برای همه‌ی کاربران یک سطل مشترک می‌شوند و IP ممیزی بی‌ارزش است.
- `docs/security/controls.md` بخش «الزامات استقرار» را دارد. تغییر کدی لازم نشد.
