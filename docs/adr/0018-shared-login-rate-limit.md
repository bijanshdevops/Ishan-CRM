# ADR 0018 — محدودیت ورود مشترک با Redis

وضعیت: پذیرفته‌شده (فاز ۱۶؛ جزئیات در PR برای بازبینی)

## زمینه

محدودیت تلاش ورود تا امروز یک شمارنده‌ی حافظه‌ای برای هر IP در هر پردازش بود. با چند نمونه‌ی API هر
نمونه شمارنده‌ی جدا دارد (محدودیت N برابر می‌شود) و با راه‌اندازی دوباره صفر می‌شود. فقط IP هم کافی نیست:
حمله‌ی پخش‌شده از چند IP روی یک حساب از آن رد می‌شود. قفل حساب بعد از چند شکست از قبل در دیتابیس هست
(`LOGIN_MAX_FAILURES`) و بدون تغییر می‌ماند.

## تصمیمات

1. **سرویس `RateLimitService`** (زیرساخت): شمارنده‌ی پنجره‌ی ثابت در Redis با یک اسکریپت Lua اتمیک
   (`INCR` و `PEXPIRE` در یک گام؛ کلید هرگز بدون انقضا نمی‌ماند). کلیدها پیشوند `rl:` دارند.
2. **دو شمارنده برای ورود:** به‌ازای IP (`LOGIN_RATE_LIMIT_PER_MINUTE`، پیش‌فرض ۲۰) و به‌ازای نشانی ایمیل
   (`LOGIN_RATE_LIMIT_PER_ACCOUNT_PER_MINUTE`، پیش‌فرض ۱۰). کلید حساب هش SHA-256 ایمیلِ کوچک‌شده است، نه
   خود ایمیل. هر دو شمارنده همیشه شمرده می‌شوند.
3. **بدون Redis یا هنگام قطعی:** بازگشت به پنجره‌ی حافظه‌ای همان پردازش. دلیل: قطعی Redis نباید ورود را
   قفل کند (fail-open به محدودیت محلی، نه بدون محدودیت). اتصال با `enableOfflineQueue: false` و timeout
   کوتاه ساخته می‌شود تا درخواست ورود منتظر Redis نماند. هشدار لاگ حداکثر دقیقه‌ای یک‌بار.
4. **پیامد شناخته‌شده:** مهاجم می‌تواند با تلاش‌های ساختگی روی یک ایمیل، ورود صاحب آن را تا یک دقیقه
   کند کند. این از قفل حساب فعلی ضعیف‌تر است (که بیشتر طول می‌کشد)، و آستانه‌ی محدودیت ایمیل قابل تنظیم است.
5. **دامنه:** فقط ورود؛ بقیه‌ی محدودکننده‌ها در ADR 0022 همین سرویس را گرفتند.

## پیامدها

- متغیر جدید: `LOGIN_RATE_LIMIT_PER_ACCOUNT_PER_MINUTE`. در `compose.dev.yml` برای تست‌های مرورگر (که چندین
  بار با یک مدیر وارد می‌شوند) روی ۱۰۰۰ است.
- تست: واحد با کلاینت جعلی (اشتراک شمارنده بین دو نمونه، fallback)، یکپارچه با Redis واقعی (انقضا،
  Redis در دسترس نیست) و HTTP (۴۲۹ بعد از آستانه‌ی حساب، حساب دیگر بی‌تأثیر).
